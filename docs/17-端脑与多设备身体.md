# 17 端脑与多设备身体

> 一句话：它是一颗脑，不是一个程序——脑在核心，身体在设备；同一个体可以换身体，但同时只有一个意识流。

本文把蓝图从"单机上跑的一个进程"扩展成"可安装在手机、电脑、服务器、机器人上的一个个体"。它不改三条公理，但要把 [02 系统架构](./02-系统架构.md) 的 L1 身体层**拆成两半**：身体接口（抽象）留在核心，身体实现（设备节点）外置。

---

## 0. 三条硬约束（先立规矩）

| 编号 | 约束 | 为什么 |
|---|---|---|
| C1 | **核心是唯一写者**。任何设备都不能直接写个体状态（记忆、特质、自传、关系） | 多写者 = 多人格；A3 不可逆优先要求状态只有一条时间线 |
| C2 | **身体不直连依赖**。LLM、记忆库、媒体库只由核心访问，设备不持有副本 | 你说的"访问的都是一个个体"，物理上就是依赖只挂在一处 |
| C3 | **能力 = 设备能力 ∩ 阶段解锁 ∩ 用户授权** | 设备能做的、它这个年纪能做的、你允许它做的，三者取交集 |

---

## 1. 为什么现在必须改

现有设计隐含了四个"单机假设"，多设备一上来就全破：

| 假设 | 冲突 | 后果若不改 |
|---|---|---|
| 一个进程同时是脑和身体 | 手机会锁屏、机器人会断电、服务器会重启 | 进程一停，"人"就死了 |
| 时钟即真实时间 | 设备时钟不同步、离线数小时 | episode 顺序错乱，巩固算错先后 |
| 动作即本机副作用 | 手机的通知、机器人的轮子 | 为了跨设备要复制核心逻辑，必然分裂状态 |
| 一个身体一个注意力 | 手机和机器人都"在场" | 两条 episode 流 → 两个人格 |

所以先做一件事：**把"它"从"跑它的进程"里拿出来。**

## 2. 目标架构

```
                    ┌──────────────────────────────┐
                    │  端脑核心 cerebrum (单写者)    │
                    │  L2 发育引擎 / L4 记忆 / L5 观察台│
                    │  依赖接口：LLM · Memory · Media │
                    └──────────────┬───────────────┘
                                   │  WebSocket / mTLS
        ┌──────────────┬───────────┴───────────┬──────────────┐
        │              │                       │              │
   ┌────▼────┐   ┌─────▼─────┐          ┌──────▼─────┐  ┌─────▼─────┐
   │ 手机身体 │   │ 电脑身体   │          │ 服务器身体  │  │ 机器人身体 │
   │ 感知/通知│   │ 文件/键鼠  │          │ 常驻/存储   │  │ 轮子/舵机  │
   └─────────┘   └───────────┘          └────────────┘  └───────────┘
```

四层分工：

- **端脑（core）**：个体身份、状态、episode 循环、巩固、阶段判定、安全出口、依赖访问。可以有备份，但**同一时刻只有一个主核心**（主备切换，不双活）。
- **身体节点（body）**：能力清单 + 传感器 + 执行器 + 本地安全 + 缓冲。**无个体状态**，可随时销毁重建。
- **依赖接口**：LLM / Memory / Media / Notification，都是可替换的适配器，只被核心调用。
- **传输**：WebSocket + JSON，消息带 nonce 与单调序号，幂等。

一句话：**脑随身走，身体随地换。**

## 3. 谁是"它"

这是最先要回答的问题，因为它决定数据放哪。

| 问题 | 答案 |
|---|---|
| "它"是核心还是设备？ | 核心。设备是它的身体，换掉身体它还是它 |
| 记忆存在哪？ | 只有核心。设备只缓存 UI 状态与未提交的观察 |
| 它能同时用两个设备吗？ | 能，但只有一个**焦点身体**产生 episode（§5） |
| 它换到手机上之后，PC 还算它吗？ | PC 降级为**背景身体**：可执行低层动作，不产生独立经历 |
| 关机时它"睡了吗"？ | 没有它，就没有它。离线是"不存在"，不是"睡着"（与 09 同口径） |

最后一条很重要：不能写"它睡了 8 小时"，只能写"核心离线 8 小时，期间无 episode"。**假装连续是对"一个个体"的最大伪造。**

## 4. 单写者与在场：租约、心跳、切换

### 4.1 租约

```
lease = { body_id, focus: bool, ttl_s: 15, epoch: int }
```

- 核心向**一个**身体发 `focus=true` 租约，`epoch` 单调递增；
- 身体每 5 s 发心跳，续租；
- 15 s 无心跳（3 次丢失）→ 核心撤销租约，进入 `absent` 态；
- 旧 epoch 的动作请求一律拒绝（防脑裂后的僵尸身体）。

### 4.2 切换状态机

```
attached(focus) --detach(reason)--> detaching --ack--> detached
detached --attach(new_body)--> attaching --lease--> attached(focus)
```

`reason ∈ {user_moves, focus_switch, device_sleep, battery, network, robot_safety}`。每次切换写一条 `body_handoff` 事件：谁、何时、为什么、切换前最后一个动作。

### 4.3 副核心（备）

允许热备，但**不双活**：备核心只做只读复制与日志追赶，主核心失联超过 `failover_after_s = 60` 才提升，提升前必须拿到最后一条事件的哈希与单调时钟，避免"两个过去"。

## 5. 一个意识流，多个身体

人一边走路一边听歌，但注意力只有一条。架构上照这个来：

| 角色 | 定义 | 能做什么 | 产生 episode 吗 |
|---|---|---|---|
| **焦点身体** | 当前注意所在 | 全部已解锁动作 + 全部感官 | 是 |
| **背景身体** | 在跑但不被注意 | 只允许"预批准的低层程序"（走路、播放、保持姿态） | 否 |
| **休眠身体** | 离线或未授权 | 无 | 否 |

规则：

1. 同一时刻焦点身体**唯一**（`epoch` 保证）；
2. 背景身体的动作必须是**可并行的低层程序**，不得与焦点动作冲突（核心维护 `action_lock`）；
3. 背景身体的动作仍进事件日志，但标 `background: true`，**不计入特质投影**（它们的"选择"不是注意的选择）；
4. 焦点切换时，背景程序可以继续，但它的观察不再进入注意流。

这条规则解决了一个很容易做错的地方：**多设备不等于多个自我**。谁注意，谁就是此刻的"我"。

## 6. 能力模型与授权

### 6.1 身体清单

```json
{
  "body_id": "phone-01",
  "kind": "phone",
  "caps": {
    "sense": ["camera", "mic", "location", "motion", "screen_state", "notif_in"],
    "act": ["notify", "tts", "display", "vibrate", "flashlight", "open_app"],
    "limits": { "max_actions_per_min": 30, "display_area": "6.1in" }
  },
  "safety": { "physical": null },
  "transport": { "ws": "wss://core.lan:7443/body", "auth": "ed25519" }
}
```

机器人额外有 `physical` 段：最大速度、力矩、工作域、急停方式。

### 6.2 三层交集

```
effective = body.caps.sense ∪ body.caps.act
          ∩ unlocked(stage)          # 08 的能力门控
          ∩ granted(scopes)          # 用户逐项授权
```

任何一项不在交集里，动作在**核心侧**就被拒绝（不是等设备拒绝）。设备侧再做一次本地检查——**双点拦截**，因为核心可能被绕过而设备不会。

### 6.3 授权粒度

| 维度 | 例子 |
|---|---|
| 设备 | 只允许家里的 PC，不允许公司电脑 |
| 能力 | 允许相机，不允许麦克风 |
| 情境 | 只在前台时允许定位；只在 8:00–22:00 允许通知 |
| 时长 | 授权到某个日期，到期自动失效 |
| 撤销 | 随时一键撤销，撤销事件写进审计链 |

### 6.4 授权即教育

授权不是纯技术。**"什么允许它做"本身就是它的成长环境**：一个从小只在手机上、只能看不能动的个体，和一个有机器人身体、能走能碰的个体，会长成两种人。这条要写进产品文案，否则用户以为只是权限设置。

## 7. 传输协议

消息统一信封：

```json
{ "v": 1, "type": "observe", "id": "msg-...", "ts": "...", "seq": 42, "body_id": "phone-01", "payload": {} }
```

| 类型 | 方向 | 说明 |
|---|---|---|
| `hello` | body→core | 清单 + 公钥 + 版本 |
| `lease` | core→body | 焦点/背景/撤销，带 epoch 与 ttl |
| `observe` | body→core | 一次感知（已按阶段裁剪前的原始字段） |
| `action_req` | core→body | 动作 + 参数 + deadline + `safety_token` |
| `action_res` | body→core | 成功/失败/被本地安全拒绝（带原因码） |
| `heartbeat` | 双向 | 电量、前台状态、延迟 |
| `revoke` | core→body | 撤销某能力，立即生效 |

约束：

- 每条消息幂等（`id` 去重，保留 24 h）；
- `seq` 单调，用于发现丢包与重放；
- `safety_token` 由核心签发，含阶段、能力、有效期，设备侧验签后才执行——**防止旧指令被重放去动机器人**。

## 8. 离线：观察不等于经历

设备离线时能做什么、不能做什么，必须写死：

| 场景 | 允许 | 禁止 |
|---|---|---|
| 手机锁屏 2 小时 | 缓冲通知、位置、屏幕状态（本地，加密） | 生成 episode、调用 LLM |
| 机器人断网 30 秒 | 执行已下发的动作直到 deadline | 自主新动作、修改状态 |
| 核心离线 1 天 | 各身体进入 `absent`，只做本地最小功能 | 任何身体自封为核心 |

重连后：

1. 身体上传缓冲观察，核心标 `external_event`；
2. 核心**可以**在巩固时把它当作"世界信息"吸收（"我不在的时候，家里门开了"），但**不得**把它伪装成"我经历过"；
3. 连续离线超过 `offline.catchup_horizon_h = 72` 的观察直接折叠成一条摘要，不逐条补（[09](./09-日常运行与调度.md) 的追赶规则同样适用）。

这条不是洁癖：**把别人的观察记成自己的经历，是在伪造一个人的传记。**

## 9. 安全

多设备把攻击面从"一个进程"扩大到"一个网络"。

| 层 | 措施 |
|---|---|
| 配对 | 设备首次接入需核心侧确认（扫码/短码），绑定公钥 |
| 传输 | mTLS 或 ed25519 消息签名 + 时间窗（±60 s）防重放 |
| 指令 | `safety_token` 绑定阶段与能力；设备侧独立验签 |
| 物理 | 机器人：硬急停优先于软件、速率/力矩上限、工作域围栏、人在场检测 |
| 撤销 | 核心一键 revoke；设备本地也有一键停 |
| 审计 | 每个动作双端留日志，可对账 |
| 隐私 | 相机/麦克风默认关；采集即加密；不得上传到核心以外 |

红线不变（[11](./11-安全与伦理.md)）：不声称意识、不表演痛苦、不情感勒索。**设备数量不改变这些。**

## 10. 依赖接口

核心访问外部资源只通过四个接口，全部可替换：

```
LLMProvider   : complete(req) -> resp            # OpenAI 兼容 / 本地模型
MemoryStore   : put/query/supersede              # SQLite 本地 / 远端同步
MediaSource   : stream(day) -> [visual_item]     # 本地快照 / 平台适配器
Notifier      : push(body_id, msg)               # 由哪只手把话递出去
```

关键是**边界的形状**：设备只提交"感知"、接收"动作"，**永远不调用 LLM 或记忆**。这条不写死，多设备就会各自长出记忆，个体就分裂了。

未来若把记忆放到远端服务，只需换 `MemoryStore` 实现，核心逻辑不动。

## 11. 部署形态

| 形态 | 核心放哪 | 身体 | 适用 |
|---|---|---|---|
| 单机（v0） | 同一台 PC | 本机 | 现在就能做，M0 |
| 家庭（推荐） | 常开的小主机/服务器 | 手机、PC、机器人 | 长跑实验的稳态 |
| 随身 | 手机（前台时） | 手机 + 蓝牙外设 | 演示，不适合长跑 |
| 混合 | 家为主核心，手机为漫游身体 | 多设备 | 需要 §4 的切换与离线规则 |

**建议**：v0 单机 → v1 家庭常开核心 + 手机身体（最容易验证切换与离线）→ v2 机器人身体（验证物理安全）→ v3 多身体并行（验证注意力模型）。

## 14. 风险

| 风险 | 触发 | 缓解 |
|---|---|---|
| 脑裂（两个"它"同时写） | 网络分区 + 备核心误提升 | 单写者 + epoch + 哈希链校验；宁可停也不双活 |
| 身体接管 | 设备被攻破 | 设备侧验签 + 能力白名单 + 硬急停 |
| 机器人伤人 | 动作越界、人在场 | 物理急停优先、力矩上限、围栏、双点安全门 |
| 隐私外泄 | 相机/麦克风长期开启 | 默认关 + 前台会话 + 采集加密 + 可审计 |
| 注意力分裂 | 多身体都想产生 episode | 焦点唯一 + 背景动作不计入投影 |
| 长延迟导致"人"卡顿 | 异地网络 | 本地反射白名单（已预批准）+ 焦点就近选择 |

## 15. 与 00 的关系

新增四条裁定（记入 [00 §14](./00-核心设计约定.md)）：

| 编号 | 裁定 |
|---|---|
| D-10 | 个体 = 单写者核心 + 多身体节点；同一时刻焦点身体唯一；背景身体可并行但不算经历 |
| D-11 | 设备不持有状态、不直连 LLM/记忆；离线观察只能是 `external_event` |
| D-12 | 能力 = 设备能力 ∩ 阶段解锁 ∩ 用户授权；核心与设备双点拦截 |
| D-13 | 传输需配对、签名、防重放；机器人物理急停优先于一切软件指令 |

一句话总结本文：**你可以把它装进任何设备，但你永远不会同时得到两个它。**
