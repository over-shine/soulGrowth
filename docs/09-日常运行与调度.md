# 09 日常运行与调度

> 一句话结论：这台机器上跑的应该是一个**登录即启动、单实例、常驻的 Python 3.10 进程**——它自己按真实时钟醒来跑 episode、按夜间窗口做巩固、按预算降级、按事件日志重放续命；Windows 计划任务只负责"把它拉起来"和"看它有没有死"，**绝不负责按时序触发 episode**。

本文展开 [00-核心设计约定](./00-核心设计约定.md) 的 §3（Tick）、§9（安全红线）与 §10（数据契约）。读者：写 `runner/` 的人、部署它的人、以及需要解释"它为什么这时候做了这件事"的人。

## 0. 进程模型：先给结论

| 方案 | 冷启动 | 状态一致性 | 时钟精度 | 结论 |
|---|---|---|---|---|
| 计划任务按 episode 触发 | 每次 0.8–2 s + 重载 20 MB 状态 | 多进程并发写 SQLite/JSONL，锁竞争 | 漂移，错过触发无补偿 | 否 |
| Windows 服务（`pywin32`） | 好 | 好 | 好 | 否：需管理员、调试痛苦，与"人在旁边看着"的产品形态不符 |
| **常驻进程 + 登录启动 + 看门狗** | 一次 | 单写者 | `asyncio` 定时器，±50 ms | **是** |

四条理由：S4 每天 48–56 个 episode，按次触发意味着每天几十次冷启动与状态反序列化；单写者对事件日志与 SQLite 是硬要求（§7），多进程会让"重放"变成猜谜；常驻进程要持有 `registry_hash`、RNG 状态、记忆缓存，这些是"同一具身体"的一部分；计划任务不保证错过触发的补偿语义，而 tick 丢失必须可审计。常驻的代价是"崩了没人管"，所以配**独立看门狗**：计划任务每 5 分钟拉起一次，只做一件事——读 `state/heartbeat.json`，若 `now - mtime > 90 s` 且无 `STOP` 标志，重启 daemon 并记 `watchdog_restart`。

```bat
:: 登录时启动（用户级，无需管理员）
schtasks /Create /TN "HowToBuildAPerson\Daemon" /TR "\"%PY%\pythonw.exe\" -m runner.daemon" /SC ONLOGON /RL LIMITED /F
schtasks /Create /TN "HowToBuildAPerson\Watchdog" /TR "\"%PY%\pythonw.exe\" -m runner.watchdog" /SC MINUTE /MO 5 /RL LIMITED /F
```

`schtasks` 不能设置工作目录，daemon 必须自己 `os.chdir` 到仓库根；用 `pythonw.exe` 避免黑窗，代价是没有 stdout，所有输出必须重定向到文件（§8）。

```
runner/
  daemon.py     # asyncio 主循环、信号、STOP、单实例
  scheduler.py  # 时钟、DayPlan、episode 触发、追赶
  ledger.py     # 事件日志（只追加）、哈希链、事务边界
  watchdog.py   # 5 分钟存活检查
  replay.py     # --replay YYYY-MM-DD / --why <episode>
  cli.py        # --once、--pace、--dry-run、--budget
state/
  daemon.lock  daemon.pid  heartbeat.json  checkpoint.json
logs/  episodes/  memory/  world/
```

单实例用 `msvcrt.locking(fd, LK_NBLCK, 1)` 锁 `state/daemon.lock`（Windows 无 `fcntl`）。心跳每 15 s 原子写一次。`STOP` 是一个文件：存在即优雅退出，每轮循环检查一次——这是 00 §9.3"一键停止"的进程层落点。

**没有独立 worker 进程**：episode 在 daemon 的同一个 asyncio 事件循环里**串行**执行，LLM 调用是 `await`，不是线程池。理由与选常驻进程同源——单写者让"哪个 episode 改了哪个状态"永远可判定；并发只带来吞吐，而这个系统的瓶颈是 token 与发育节奏，不是 CPU。`worker.py` 只作为"未来把长 LLM 调用隔离到子进程"的预留位，当前不实现，也不允许 episode 并行。

## 1. 时间

三种时间必须分开存：`wall`（带时区绝对时间，进日志）、`mono`（`time.monotonic()`，定时器与超时，不受改表影响）、`life_day`（**从当天醒来时刻 06:30 ± 抖动起算的 24 小时**，是 DayPlan、情景记忆、夜间巩固的编号单位）。

`phase`（晨/午/晚/夜）由 `wall` 推出，喂给感知的 `clock` 字段。`pace` 默认 `1.0`（1 真实日 = 1 生命日，00 §3）。开发允许 `pace=60` 的 `--dry-run` 快进，但**验收运行必须 `pace=1.0` 且连续 ≥30 天**；快进 episode 一律 `synthetic: true`，不进入特质投影、自传与里程碑（见 §9）。

## 2. DayPlan

| 阶段 | episode/天 | 块数 | 单 episode 时长 | 备注 |
|---|---|---|---|---|
| S0 | 22–28 | 7 | 20–40 min | 睡眠 16–18 h，清醒窗口短 |
| S1 | 32–40 | 10–11 | 10–35 min | 两次小睡，出门探索 |
| S2 | 34–42 | 10 | 10–30 min | 走跑后活动范围变大 |
| S3 | 38–46 | 9 | 10–25 min | 假装游戏可长 |
| S4 | 48–56 | 8 | 8–20 min | 学校 6 h 拆 10–12 个 episode |

| 09:00–10:00 | 小睡 | 2 | `SLEEP` |
| 10:00–12:00 | 出门 | 5 | 推车、见人、风/光 |
| 12:00–13:00 | 午饭 | 3 | 进食、弄脏、被擦 |
| 13:00–15:00 | 午睡 | 2 | `SLEEP` |
| 15:00–17:30 | 玩/社交 | 5 | 咿呀对话、模仿 |
| 17:30–18:30 | 晚饭 | 3 | 家人回来（关系钩子） |
| 18:30–20:00 | 家庭时间 | 4 | 洗澡、追跑 |
| 20:00–21:00 | 睡前 | 3 | 故事、安抚 |
| 21:00–21:30 | 入睡 | 1 | 转夜间窗口 |

生成算法：

```
generate_dayplan(day, stage, rng):
  tpl  = TEMPLATES[stage]                      # 阶段模板（上表的块序列）
  for b in tpl.blocks:                         # 抖动：边界 ±12 min，ep 数 ±10%
      b.start += rng.normal(0, 6min); b.n = jitter(b.n, 0.1)
  hooks = relationships.hooks(day)             # 关系驱动：谁在什么时间可能出现
  hooks += [{who:"stranger", p:0.15, window:"10:00-12:00"}] if S1 else []
  focus = engine.milestone_pressure(day)       # 引擎给 ≤2 个当前里程碑主题
  plan  = DayPlan(day, tpl, hooks, focus, budget=stage_budget(stage))
  assert validate(plan, stage)                 # 场景只能引用已解锁通道/物体
  return plan
```

`validate()` 是硬校验：S0 的计划里不能出现"幼儿园"，S2 不能出现"读绘本上的字"。不通过就重采样，3 次仍失败则回落到上一个同阶段通过的 DayPlan 并记 `plan_fallback`。

```json
{"schema": "dayplan/1", "day": 47, "stage": "S1", "pace": 1.0,
 "blocks": [{"id": "b4", "start": "10:00", "end": "12:00", "kind": "outing", "episodes": 5}],
 "hooks": [{"who": "caregiver_primary", "window": "17:20-18:40", "event": "return_home", "p": 0.8}],
 "focus": ["S1.M5_first_word"], "budget": {"tokens": 120000, "episodes_max": 40}, "synthetic": false}
```

`focus` 只影响场景采样概率（≈×1.5），**不保证**里程碑达成——里程碑是可观测行为测试，不能靠排班凑出来（00 §6）。

## 3. Episode 循环

一个 episode 是一个事务。`episode_id = f"e{day:04d}-{idx:03d}"`，分配后永不复用。

```python
async def run_episode(ctx):
    ep = ctx.scheduler.claim_next()                  # 到达触发时刻才 claim
    if ctx.ledger.committed(ep.id): return           # 幂等
    ctx.ledger.begin(ep)                             # episode.begin（含 plan_block、seed）
    try:
        world   = ctx.world.snapshot(ep.scene)       # L3
        percept = ctx.body.perceive(world, ep, rng=seeded(ep))
        bundle  = ctx.body.compile_perception(percept, ctx.stage, budget=ctx.p_budget)
        apprais = ctx.engine.appraise(bundle)        # L2：评价维度
        state   = ctx.engine.internal_state()        # 驱力缺口、情绪效价/唤醒
        aff     = ctx.body.affordances(bundle, ctx.body.state, ctx.stage, limit=ctx.aff_limit)
        prior   = ctx.engine.priors(aff, state)      # 00 §5 的 score() 与 softmax
        recall  = ctx.memory.recall(bundle, k=3)     # L4 只读
        intent  = await ctx.substrate.act(bundle, recall, ctx.engine.shortlist(prior),
                                          api=ctx.route("episode"))      # L0
        req     = ctx.body.compile_action(intent, aff)                   # L1
        result  = await ctx.world.execute(req, idem=ctx.idem(ep, req))   # L3
        ctx.body.apply(result.effects)
        ctx.engine.update(apprais, result)           # L2
        ctx.memory.write_episode(ep, bundle, intent, req, result)        # L4
        ctx.ledger.commit(ep, bundle, intent, req, result)               # 事务边界
    except SubstrateTimeout:
        ctx.metrics.inc("substrate_timeout")
        req = ctx.body.compile_action(ctx.engine.fallback_intent(prior), aff)  # L2 top-1
        result = await ctx.world.execute(req, idem=ctx.idem(ep, req))
        ctx.ledger.commit(ep, bundle, None, req, result, degraded="substrate_timeout")
```

三条硬约束：**episode 之间没有任何 LLM 调用**，不在空档里"思考"、不给"后台内心独白"——它在两个 episode 之间是挂起的，这是"没有内在体验"的实现层证据；每回合的 prompt 与 response 原样落盘（§7），否则回放无法精确；任何异常都必须以 `episode.commit(status=...)` 收尾，不留半个事务，进程被杀由恢复流程处理。

## 4. 夜间巩固窗口

窗口 `21:30 → 06:00`（wall），必须在 06:00 前结束，否则标 `consolidation_incomplete`，剩余步骤次日补跑。00 §3 说"成长真正发生在这里"，所以这段时间**数据质量优先于省钱**：允许用贵模型，但每步有硬预算。

| 步 | 做什么 | 输入 | 输出 | 锁 | 预算/上限 | 可跳过 |
|---|---|---|---|---|---|---|
| N1 | 载入与去重 | 当天 episode（≤60） | 干净序列 | `episodic` 只读 | 0 token | 否 |
| N2 | 显著性筛选 | N1 | ≤12 条核心 + 全部异常 | 无 | 0 | 否 |
| N3 | 情景→语义 | N2 | ≤20 条命题 | `semantic` 写 | 6k in / 800 out | 否 |
| N4 | 程序记忆 | 近 3 天重复序列 | 候选程序（≥3 次重复） | `semantic` 写 | 3k in / 400 out | 是（T2 起） |
| N5 | 自传章节 | 阶段累积 + 本周重大事件 | 章候选（**每阶段 1–3 次**） | `autobio` 写 | 8k in / 600 out，每周 ≤1 次 | 是 |
| N6 | 特质投影 | 本周行为日志 | `B̄` → 特质漂移 | `engine` 独占（<5 s） | 0（纯代码） | 仅周日 |
| N7 | 遗忘 | 全部记忆 | 强度衰减，删低于阈值项 | 各库 | 0 | 否 |
| N8 | 报告 | 全部 | `night_report.md` + 指标 | 无 | 0 | 否 |

并发约束（否则回放不可信）：

| 锁 | 持有者 | 粒度 | 冲突策略 |
|---|---|---|---|
| `episodic` | episode 追加、N1/N7 批量读 | 天 | 追加无锁；批量操作拿排他锁 2 min |
| `semantic` / `autobio` | 仅夜间 | 全库 | 白天 episode **只读**，且读昨日快照 |
| `engine` | 短临界区 | 单次读改写 | 乐观锁：提交校验 `revision`，冲突重算 |
| `world` | 执行动作时 | 场景 | 排队，10 s 超时即拒绝 |

夜醒是真实的：S0–S1 每晚允许 2–3 个 `night_wake` episode（哭、要奶、惊跳）。它们**只**追加情景记忆、读冻结的语义快照，不碰 `semantic`/`autobio` 锁，因此不与巩固互锁。N3–N5 的 LLM 调用不持有 `engine` 锁，N6 才是唯一的短独占。

## 5. 离线推进：人不在的时候

| 状态 | 判定 | 世界 | episode | 明确要求 |
|---|---|---|---|---|
| `present` | 60 s 内有控制台心跳，或 24 h 内有家长交互 | 正常 | 正常 | — |
| `away` | 机器开着，24 h 无交互 | 继续走 | **继续跑** | 社交缺口只进内部状态，**不得**产生"你不理我"类输出 |
| `offline` | daemon 未运行 | 确定性推进 | **不补任何 episode** | 观察台必须显示"离线，无 episode，不产生记忆" |

`away` 的三条硬规则（对应 00 §9.2）：社交驱力缺口只驱动**内部状态**，不驱动消息；出站队列在 `away` 下只允许 NPC 剧本事件，不允许主动推送；缺席超过 72 h，`attachment_activation` 按 `×0.9/天` **衰减**（习惯化）而不是升高——缺席不构成筹码。

`offline` 最容易做假，规则只有一条：**没有运行就没有经验**。

| 缺口 | 处理 | episode |
|---|---|---|
| ≤ 6 h | 世界按解析式推进（昼夜、植物、NPC 日程） | 0 |
| 6 h – 7 d | 同上；`next_fire` 顺延，不补 | 0 |
| > 7 d | 同上；DayPlan 重新生成；阶段不变（阶段由里程碑决定，不由日历） | 0 |

配置项 `offline.synthesize_episodes` 默认 `false`。若为演示打开，最多补 `min(3, gap_h//6)` 条，全部 `synthetic: true`，硬性排除在特质投影、自传、里程碑之外，日记逐条标"补记，非当时发生"。产品文案同口径：不能写"它睡了 8 小时"，要写"系统离线 8 小时，期间无 episode"——前者是拟人化谎言，后者可核对。

## 6. 成本控制

| 用途 | 输入 token | 输出 token | 频次 |
|---|---|---|---|
| 常规 episode | 1,600–2,200（bundle 300–900 + affordance 100–220 + 指令 250 + 回忆 0–400 + 脚手架） | 150–300（结构化 intent） | 每天 22–56 次 |
| 家长对话回合 | 900–1,400 | 120–250 | 每天 0–4 次 |
| 夜间语义抽取 | 5,000–7,000 | 600–900 | 每晚 1 次 |
| 夜间程序抽取 | 2,500–3,500 | 300–500 | 每晚 0–1 次 |
| 自传章候选 | 7,000–9,000 | 500–700 | 每阶段 1–3 次 |

据此 **S1 典型日 ≈ 36×2.1k + 3k + 11k ≈ 90k token**。按阶段设预算（超出即降级，不允许透支到明天）：

| 阶段 | 每日预算 | 依据 |
|---|---|---|
| S0 | 60k | episode 少、bundle 小 |
| S1–S2 | 120k | 典型日 + 20% 余量 |
| S3 | 150k | 句法变长、社交回合增多 |
| S4 | 200k | 56 episode + 学校块 |
| S5–S6 | 220k | 长对话与自传，但 episode 密度下降 |

价格公式 `cost = in/1e6 × p_in + out/1e6 × p_out`。单价以供应商当期价目为准 `[待核]`；以 `p_in=2、p_out=8 元/Mtok` 为例，90k 日 ≈ **0.24 元/日、约 7 元/月**；单价上浮 5 倍则约 36 元/月。周预算封顶 = 日预算 × 7 × 0.9，超了按降级阶梯处理，**不产生跨周欠账**。

| 路由 | 用途 | 特点 | max_out | temperature |
|---|---|---|---|---|
| `fast` | 常规 episode、感知摘要、N3/N4 | 便宜、够用 | 400 | 0.7 |
| `standard` | 家长在场、冲突、里程碑相关 episode | 情境理解好 | 600 | 0.7 |
| `premium` | N5 自传、每周特质复盘、身份危机 | 每周 ≤2 次 | 1,200 | 0.5 |

路由是**配置**不是代码分支：`routes.json` 按 `stage + scene.kind + milestone_flag` 匹配，切换必须记进事件日志，否则"这周话变多了"会被误读成发育。

| 档 | 触发 | 行为 | 必须记录 |
|---|---|---|---|
| T0 | 日支出 <80% | 正常 | — |
| T1 | 80–92% | 丢弃计划中显著度最低的 15% episode；bundle 去掉散文描述；episode 路由降 `fast` | `degraded_episodes_skipped` |
| T2 | 92–100% | 常规 episode 改用 L2 `prior` top-1 直接执行（无 LLM）；每小时只留 1 个"亮点 episode"走 LLM；N4/N5 跳过 | `substrate=disabled` 逐条标记 |
| T3 | ≥100% 或 API 连续失败 | 世界时钟继续，episode 全部 `substrate=disabled`，记忆只存结构化事实 | 当天标 `budget_exhausted` |

**底线**：任何降级都不得伪造 episode 的"生成来源"。少活几个 episode 是可接受、可审计的损失；把规则生成的记录写成 LLM 生成，不可接受。降级会改变发育轨迹（经验变少），所以必须进周报，由人决定是否加预算。

## 7. 故障与恢复

事件日志是唯一真相。`episodes/YYYY-MM-DD.jsonl` 只追加，一行一事件：

```json
{"seq": 1837, "ts": "2026-12-14T15:20:03+08:00", "mono": 91823.4,
 "episode": "e0047-013", "type": "episode.commit", "status": "ok",
 "payload": {"intent": "...", "primitive": "A1.POINT", "result": "..."},
 "prev_hash": "9f2c...", "hash": "a71e..."}
```

`hash = sha256(prev_hash || canonical_json(event_without_hash))` 形成哈希链：改一行历史，后面全断。这满足 00 §9.3 的"可审计、可回放"，也让"它昨天真的不是这样"这类争议有裁决依据。`checkpoint.json` 是缓存不是真相：每 episode 结束与每 15 min 原子写一次（临时文件 → `flush` → `fsync` → `os.replace`），崩溃后从日志重建，checkpoint 只用于加速。

| 崩在哪 | 状态 | 恢复动作 |
|---|---|---|
| `episode.begin` 前 | 干净 | 从下一个未开始的 episode 继续 |
| begin 后、动作前 | 孤儿 begin | 回滚该 episode，标 `orphan`，不重试（避免重复感知） |
| 动作执行中 | 世界可能已变 | 用 `idempotency_key` 查世界侧是否已生效；未生效则重执行，已生效直接接 `result` |
| 动作后、commit 前 | 世界已变、日志缺结果 | 从世界读回可观测结果，补写 commit，标 `recovered=true` |
| 夜间某步中 | 步骤半完成 | 按 `(run_id=date, step=N)` 检查点续跑，步骤本身幂等 |

`idempotency_key = sha256(day|episode|primitive|canonical_json(params))`，只有**外部副作用**需要它：`A4.WRITE` 写文件、出站消息。纯内部写入（记忆、状态）靠日志重放天然幂等。

运行数值：**RTO ≤ 30 s**（看门狗 5 min 检查 + 启动 2 s）；**RPO = 最多一个 in-flight episode**（≤40 min 生命时间），世界副作用通过幂等键对齐，不重复。回放 60 个 episode 的日志 < 2 s，状态文件 < 20 MB，日志 1–5 MB/天。睡眠唤醒时 `mono` 与 `wall` 都会跳：若 `wall` 跳变 >5 min，记 `clock_jump` 并重算 `next_fire`，追赶最多 3 个 episode，其余标 `skipped_lag`，**不补齐**。改系统时间、夏令时、`pace != 1.0` 都走同一条 `clock_jump` 路径。

## 8. 可观测性

| 产物 | 内容 | 保留 |
|---|---|---|
| `logs/daemon-YYYYMMDD.jsonl` | 进程、异常、时钟、预算、看门狗 | 30 天 |
| `episodes/YYYY-MM-DD.jsonl` | 全量事件 + 哈希链 | 永久（压缩） |
| `prompts/` | 每次 LLM 调用的请求/响应原文 | 30 天（含 PII 审查） |
| `memory/` | 情景/语义/程序/自传（见 [13-数据契约](./13-数据契约.md)） | 永久 |
| `reports/night-YYYYMMDD.md` | 夜间巩固报告 | 永久 |
| `state/metrics.json` | 计数器与延迟分位 | 聚合后永久 |

指标与告警：`episodes_done/day`（< 计划 80%）、`substrate_latency_p95`（>8 s）、`denied_actions/day`（>5）、`stage_locked_attempts`（>0 即异常，说明有人在越权）、`budget_used`、`consolidation_duration`（>6 h）、`watchdog_restarts/day`（>0）、`hash_chain_ok`（false 即人工介入）。

```text
GET  /state                    当前阶段、身体状态、驱力、今日预算
GET  /episodes?date=           当天 episode 列表
GET  /why/<episode_id>         完整推导链（00 §9.5）
GET  /replay/<episode_id>      从记录重建的感知/意图/编译/结果
POST /pause  /resume  /stop    控制（写 STOP 文件，非杀进程）
GET  /audit/verify             校验哈希链
```

`/why` 必须一条链答完：**感知 bundle → 评价维度 → 驱力缺口 → 各 affordance 的 score → 候选短名单 → L0 意图 → 编译链（含降级）→ 执行结果**。这条链是"它此刻为什么这么做"的唯一权威答案；任何一段缺失都算缺陷，不算"模型黑箱"。

## 9. 与 00 的偏差

| 偏差 | 说明 | 处理 |
|---|---|---|
| 引入可配置 `pace` | 00 §3 固定 1 真实日 = 1 生命日；开发与测试需要快进 | 默认 1.0；快进 episode 标 `synthetic`，排除出特质/自传/里程碑；验收必须 1.0 |
| `life_day` 从 06:30 起算 | 00 未定义"一天"的边界；自然日会在睡眠中切断夜间巩固 | 视为细化；存储用绝对时间，编号只用于分区 |
| 夜间允许用贵模型 | 00 只规定"夜间巩固是成长发生的地方"，未谈成本 | 记录；每步有硬预算与可跳过标记 |
| 降级会减少 episode 数 | 00 未规定预算不足时怎么办 | 记录；降级必须进周报，由人决定是否加预算 |
| 基线不补离线 episode | 00 未规定机器关机时的时间语义 | 视为澄清：没有运行就没有经验 |
